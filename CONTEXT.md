# Контекст продукта: дневник голода и питания

> Продуктовое ТЗ и границы MVP.  
> Для запуска см. [README.md](README.md), для техники — [ARCHITECTURE.md](ARCHITECTURE.md).

---

## Основная идея

Бот — **личный дневник голода и питания**, а не диетолог и не система назначений.

Задача бота:
- помогать **регулярно фиксировать** чувство голода и факты приёмов пищи;
- сохранять данные **в структурированном виде** для последующего анализа;
- со временем выявлять закономерности («голод → еда → сытость») и корректировать режим питания на их основе.

Бот **не заменяет** врача или диетолога.

---

## Цель пользователя

- **Похудение**
- **Работа с перееданием / РПП**

Особенности организма на этапе MVP **не моделируются** — только **накапливаются данные** для будущего анализа.

---

## Шкала голода (0–10)

| Значение | Смысл |
|----------|--------|
| 0 | Полное отсутствие голода, возможна тяжесть после еды |
| 1–2 | Лёгкое чувство, можно есть, но не обязательно |
| 3–4 | Умеренный голод, комфортно начать приём пищи |
| 5–6 | Явный голод |
| 7–8 | Сильный голод |
| 9–10 | Очень сильный голод, дискомфорт |

---

## Целевой режим питания

**3 основных приёма пищи + перекусы** — личный ориентир для анализа, не ограничение бота. Перекусов может быть сколько угодно.

Типы приёмов в боте:
- завтрак
- перекус
- обед
- ужин

Несколько перекусов за день — отдельные записи с одним типом `перекус`; различаются по **времени**.

## MVP — что входит

### 1. Запись чувства голода

- Шкала **0–10** (кнопки или короткая команда).
- Запись **в любой момент** — без ожидания напоминания.
- Каждая запись сохраняется с **меткой времени**.

### 2. Запись приёма пищи

Максимально просто и коротко. Главное — **зафиксировать факт приёма пищи**.

Минимальный сценарий:
1. Пользователь нажимает «Поел(-а)».
2. Кнопками выбирает **тип приёма** (завтрак / перекус / обед / ужин).
3. Кнопками указывает **голод до** (0–10) и **сытость после** (0–10).
4. Выбирает **время приёма** — «Сейчас», быстрый сдвиг (−15/−30/−60 мин) или ввод `ЧЧ:ММ`.

В БД: `ate_at` = фактическое время еды; `created_at` = когда запись внесена.

Свободный текст и теги еды — **не в MVP** (добавим позже).

### 3. Напоминания

| Триггер | Действие |
|---------|----------|
| **Утром** | Напоминание в заданное время пробуждения |
| **N часов без записей** | Первое inactivity-напинание (N = per-user, см. `.env`) |
| **Ещё N часов после первого напоминания** | Второе inactivity-напоминание — если по-прежнему нет записей |
| **После второго напоминания** | Больше inactivity-напоминаний не отправляем — ждём утреннего |

**Что считается активностью:** запись голода **или** запись приёма пищи.

**Логика inactivity-напоминаний (за день до следующего утра):**

1. Прошло **≥ N ч** с последней записи (голод или еда) → **первое** напоминание. *N задаётся в `.env`: `USER_{id}_INACTIVITY_HOURS`.*
2. После первого напоминания прошло **≥ N ч**, новых записей нет → **второе** напоминание.
3. После второго — **тишина до утра** (следующее inactivity-напоминание только после утреннего).
4. Любая новая запись (голод или еда) **сбрасывает** счётчик: отсчёт N ч начинается заново, можно снова получить до двух напоминаний в этом цикле.
5. **Тихие часы** (`SLEEP_TIME` → `WAKE_UP_TIME`): inactivity-напоминания не отправляются.
6. **Утреннее напоминание** начинает новый день и сбрасывает состояние inactivity-цикла.

Запись голода и приёма пищи **всегда доступна вручную**, независимо от напоминаний.

### 4. Хранение данных

- Все записи сохраняются **структурированно** (БД).
- Поля записи (ориентир):

| Поле | Описание |
|------|----------|
| `created_at` | Когда запись внесена в бот (UTC) |
| `ate_at` | Фактическое время приёма пищи (для meal; UTC) |
| `type` | `hunger` или `meal` |
| `hunger_level` | 0–10 (для type=hunger) |
| `meal_type` | breakfast / snack / lunch / dinner |
| `hunger_before` | 0–10 (для type=meal) |
| `satiety_after` | 0–10 (для type=meal) |

### 5. Экспорт данных

- Выгрузка накопленной статистики в **CSV** (открывается в Excel).
- Способ реализации — на усмотрение разработки: **по запросу** и/или **регулярный автоматический бэкап** — выбираем более простой вариант.

### 6. Пользователь и язык

- **До 2 пользователей** (whitelist по Telegram ID в `.env`).
- У каждого — свои записи, настройки пробуждения и интервал inactivity.
- Интерфейс: **только русский**.

### 7. Настройки MVP

- **Время пробуждения** — per-user, через `/settings` (хранится в БД).
- **Интервал inactivity** — per-user, только в `.env` (`USER_{id}_INACTIVITY_HOURS`).
- Часовой пояс и тихие часы — общие в `.env` (`TIMEZONE`, `SLEEP_TIME`).

## Пример сценария дня (MVP)

1. **08:00** — утреннее напоминание → голод **4**
2. **08:15** — «Поел(-а)» → завтрак, голод до **4**, сытость после **7**
3. **11:00** — вручную записала голод **5**
4. **12:30** — «Поел(-а)» → обед, голод до **6**, сытость после **8**
5. **15:00** — первое напоминание (N ч без записей) → голод **3**
6. **17:00** — второе напоминание (ещё N ч тишины) → без ответа → ждём до утра
7. **19:00** — «Поел(-а)» → ужин (запись вручную всегда доступна)

## Принципы разработки MVP

1. **Сначала сбор данных** — анализ и красивые отчёты потом.
2. **Минимум трения** — каждая запись за ≤3 нажатия.
3. **Факт важнее деталей** — лучше короткая запись, чем пропуск.
4. **Не диетолог** — бот не даёт медицинских советов и не строит рацион.
